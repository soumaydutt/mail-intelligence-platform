# Data classification and release gates

This single-host deployment serves one trusted operator on loopback. It does not provide tenant boundaries, per-user accounts, consent capture, data-subject workflows, automated deletion, or legal-hold semantics. Do not expose it publicly until an owner approves those controls and their tests.

| Location | Data | Persistence | Current control | Unapproved policy |
| --- | --- | --- | --- | --- |
| PostgreSQL `email_validation_history` | Full submitted address, DNS/status and timestamp | Durable volume and archives | Production validation requires administrator key; network private | Retention period, access purpose and erasure |
| PostgreSQL jobs and imports | Address, idempotency metadata, result, CSV rows, errors | Durable volume and archives | Shared administrator key; input bounds and formula-safe export | Retention, subject erasure and consent |
| PostgreSQL evidence and suppression | Address, delivery event and suppression reason | Durable volume and archives | Shared administrator key; audit/revocation paths | Retention, legal hold and erasure |
| Valkey | HMAC peer bucket keys, disposable DNS answers and quota state | Memory-only; cleared on restart | ACL password, private bridge, bounded memory | DNS egress authorization |
| Browser | Session-only entered administrator key, current view and downloads | Browser memory; downloaded CSV persists on operator disk | Same-origin TLS, no cookies or local key storage | Secure deletion of downloaded files |
| Logs/metrics | New request IDs, coarse routes/outcomes and worker counts omit addresses and keys; framework and error logs may still carry personal data | Container driver rolling local logs | Low-cardinality tags, no full URL/request body in new metrics; host access controls required for all logs | Full redaction review, log access, retention and incident response |
| Backup archive | Full PostgreSQL data, including information later deleted from live DB | Operator-controlled external file | Unique archive, isolated test restore | Encryption keys, expiry, destruction, recovery ownership |

No automatic cleanup is enabled: deleting live data without resolving dependent rows, idempotency, audit events, archives and legal holds risks irreversible corruption or false erasure promises. A release owner must approve retention periods, complete deletion semantics, backup rotation/encryption, and subject-access workflow. Until then: prevent public exposure; store any disposable tests only in project-unique volumes, remove only test-owned resources after inspection, and keep production backup archives out of Git. Operators must authorize DNS network egress and certificate provisioning separately. SMTP verification and sending stay disabled in the API.

The shared administrator key grants access to **all** administrative records. Generate a high-entropy random value outside Git; rotate it in the mounted secret file and restart API and worker together. The reverse proxy discards client forwarding headers and binds loopback by default. The backend's public peer quota collapses to the proxy socket; no per-client distributed guarantee is asserted. Wrong-key attempts consume shared Valkey admission before returning 401. A public or multi-operator deployment needs identity, owner-scoped authorization, ingress abuse limits, trusted peer accounting, and a new privacy review.

## Decision matrix for owner approval (no retention rule is active)

| Record and copies | Purpose and access today | Retention decision required | Erasure and legal-hold decision required |
| --- | --- | --- | --- |
| `email_validation_history` and `verification_job` | Submitted address, domain, result and immutable completed snapshot; one shared operator key, private PostgreSQL | Set separate periods for synchronous history, queued/failed/completed jobs and result evidence; define start event and audit record | Define subject matching across raw address, normalized key and job history. Linked `email_validation_history.job_id` references a job; decide whether to preserve aggregate evidence or remove both. No job/history erasure route exists. |
| `import_batch` and `import_row` | Per-file ordinal, accepted/rejected address and duplicate linkage; shared-key results/export | Set batch/row periods, rules for unfinished work and failed staging; approve CSV export access | Decide transaction boundary for rows referencing a batch/job and `duplicate_of` self-references. Cancel or fence active workers before any approved erasure; an import cancel is not data deletion. |
| `delivery_identity`, `delivery_event`, `delivery_suppression` | Canonical address key, source/external IDs, event timestamps, revocation and suppression audit; shared operator key | Set evidence, suppression and audit periods by purpose; decide whether deduplication keys must outlive event data | Resolve mandatory audit preservation versus subject erasure. Suppressions reference identity and possibly event; events reference identity. Revoking/lifting is an auditable state change, not erasure. Decide legal holds and replacement for idempotency provenance before deletion. |
| Valkey DNS entries and hashed rate buckets | Rebuildable DNS routing observations and peer-admission counters; private ACL | Approve DNS observation TTL and egress; current TTL caps are 30 seconds positive, 5 seconds negative | Valkey restart flushes these entries but does not delete PostgreSQL or backups. HMAC keys are pseudonymous, not guaranteed anonymous. |
| Browser memory and downloaded CSV | Current operator session and local export; administrator key only in memory | Approve device-use, download handling and disposal rules | Disconnect/reload clears session state, not downloaded files, screenshots, swap, or operator browser artifacts. Operator must control exports separately. |
| Container/framework logs and metrics | Coarse counts plus diagnostic errors; local rolling driver, operator-only access | Set host/export log period and restrict access; review third-party framework and database error messages for address disclosure | Review copied logs, diagnostic bundles and monitoring systems. Fixed metric labels do not prove all downstream logs free of personal data. |
| PostgreSQL volume, custom-format archives and restored test targets | Full recoverable address/event/job history, including records later removed from primary | Approve encryption at rest/in transit, key custody, archive schedule, expiry, off-host copies and recovery-point objective | Decide expiry/destruction across every copy, legal-hold exceptions and disclosure if an older archive reintroduces erased data. The current script makes no expiry or destruction claim. |

Approval record must name the data controller/operator, lawful purpose, authorized readers, each period and trigger, legal-hold authority, subject verification process, archive expiry, recovery reconciliation and evidence of deletion. All fields remain **unapproved**. There is no subject-search, export, purge or hold API. A read-only inventory can locate candidate records, but neither that inventory nor a successful isolated restore proves safe deletion. Before adding deletion, test a single fenced transaction against every foreign key and immutable audit rule on a disposable restored database, then test recoveries from an archive past the approved erasure boundary. Until the policy is signed, retain data under restricted access; never run an ad hoc production DELETE or present cancellation/revocation as erasure.
