# Phase 12 single-host deployment contract

Status: locally exercised on disposable Docker Compose stacks with a generated localhost certificate, real Chromium, API/worker import/export and isolated PostgreSQL restore. This is a trusted **single-operator, single-host candidate**, not an authorized public or multi-user service. The rebuilt images had zero HIGH/CRITICAL findings in local Trivy scans; hosted CI and operator policy gates remain open. See [release readiness](RELEASE_READINESS.md).

```
Browser -- HTTPS --> proxy (static React assets and exact same-origin API paths)
                       |-- api:8080 (HTTP; only private Compose bridge)
                       |-- api:8081 (private Actuator; only health proxied)
api, headless worker -- PostgreSQL 17 (persistent named volume; Flyway V1–V5)
api, headless worker -- Valkey 8 (disposable DNS cache and shared admission)
api, headless worker -- bounded DNS resolver (operator-controlled network egress)
```

`compose.yaml` remains the existing local-development database/Valkey stack. `compose.prod.yaml` is the independent production-oriented target. Only the proxy publishes host ports: loopback HTTP and HTTPS by default. API, worker, PostgreSQL, Valkey and private metrics publish **no host ports**. Container-internal API-to-database and cache traffic is private to this one host. PostgreSQL is authoritative for history, jobs, imports, delivery evidence and suppressions; losing Valkey discards cache and quota state, not committed records. The worker is a separate headless process and continues independently of browser traffic. Back up PostgreSQL before replacing containers or applying future migrations. Do not remove its named volume during shutdown or recovery.

TLS terminates at the proxy with operator-supplied certificate and private key mounted as secrets. Disposable verification may use a generated self-signed localhost certificate; no production certificate, public DNS record or public exposure is provisioned by this repository. API credentials, database password, Valkey password and rate identity secret come from operator-provided secret files mounted under `/run/secrets/`; no credential belongs in an image, repository, browser bundle, URL or logs. A single shared administrator key grants access to **all** administrative records. Only an operator on a trusted device should enter it. Key rotation requires changing the mounted secret and restarting API and worker together; in-flight requests may fail until both agree. TLS protects browser-to-proxy traffic; internal container traffic is not separately TLS-encrypted and requires a private host/network boundary.

The backend deliberately uses the socket peer for rate-limit identity, **not** client-controlled `Forwarded` or `X-Forwarded-For`. Behind one proxy, public per-peer quotas apply to the proxy socket, not individual browser clients; the global public bucket is shared while Valkey is healthy. On Valkey outage, authenticated administrative admission fails closed with 503, while public validation uses a bounded **process-local** fallback. A Valkey restart resets disposable quota buckets. No Valkey Cluster or multi-instance API/worker topology is supported: multi-key Lua lacks a shared hash slot, the public outage fallback is process-local, and per-client proxy identity is not established. Do not infer global admission across multiple hosts.

SMTP verification is **not wired into the public API**; no arbitrary SMTP probing or sending is enabled. Constrain outbound DNS to approved recursive resolvers with host firewall/network policy; Docker Compose alone cannot enforce external DNS egress policy portably. A public listener, production DNS/SMTP egress, multi-user identities, owner-scoped authorization, retention/erasure/legal holds, backup encryption/expiry, private Valkey TLS and upstream license approval require separate operator/policy review. The default loopback binding must not be widened to public access without those approvals.

Dependency expectations: PostgreSQL and Valkey must pass real service health checks before API/worker startup; Flyway migrations run on API startup and must fail on unknown or incompatible schema. The proxy starts only after API readiness. API readiness checks dependencies, while worker health independently requires fresh successful job-dispatch and import-promotion polls. A running worker JVM is not proof of progress; each loop owns its own readiness marker and loses it on a failed poll. If PostgreSQL fails, storage requests cannot complete, but no implicit migration repair or volume reset occurs. Operator backup/restore must target a **new disposable** database when testing recovery. Keep heavy load and fault injection on project-unique disposable stacks, never production volumes.

Compose waits for the proxy's local HTTPS request to succeed before reporting startup ready; the probe bypasses certificate trust solely to check the TLS listener. External clients must still validate the hostname and certificate chain. The disposable verifier pins its generated test CA and performs that separate check.
