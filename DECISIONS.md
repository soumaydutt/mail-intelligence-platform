# MailGuard architecture decisions

These are architecture records, not claims of implementation. **Accepted** means agreed direction; **proposed** needs approval; **provisional** means a repository-audit or implementation detail still needs verification. Future changes should add a new numbered decision or explicitly supersede an earlier ID, with evidence. See [PLAN.md](PLAN.md) and [PROGRESS.md](PROGRESS.md).

## D-001 — Java 21 and Spring Boot backend
Status: **Accepted direction; Java 21 API/OpenAPI verified with test-scope H2 and disposable Docker/MySQL**, production data unverified.
Decision: Align compiler, runtime, CI, and containers on Java 21; retain Spring Boot with a compatible dependency set.
Rationale: One supported baseline limits environment drift while retaining the existing Java ecosystem.
Alternatives: Keep Java 17/23 as currently documented or replace Spring Boot.
Trade-offs/consequences: Pin Spring Boot 4.1.0 with springdoc 3.1.1; test-scope H2 isolates HTTP/startup tests but does not prove MySQL compatibility or container startup.
Audit evidence: `pom.xml:8,29-30` selects Spring Boot 4.1.0 and Java 17; `Dockerfile:1` and README select Java 23. The sole context test fails at datasource setup, so it does not establish API or springdoc runtime compatibility.
Implementation evidence (2026-10-15): `pom.xml` compiles for Java 21; `Dockerfile` selects Temurin 21. `mvn -B test` passed two offline HTTP tests. The app started on Java 21 with test-scope H2; live `/api/email/validate` (malformed input), `/v3/api-docs`, and Swagger UI returned HTTP 200. Docker and production database were not tested.
Subsequent runtime evidence (2026-10-15): The Java 21 Docker image started against a disposable MySQL 8.4.11 container; two synthetic requests persisted two history rows. Production data and restart persistence remain unverified; see PROGRESS.md.

## D-002 — React, TypeScript, and Vite client
Status: **Accepted direction**; scope of initial UI is provisional.
Decision: Build a separate frontend consuming a documented API.
Rationale: Type safety and a locally runnable client without binding domain rules to server templates.
Alternatives: Server-rendered pages or no UI.
Trade-offs/consequences: Separate toolchain and contract testing; do not duplicate outcome policy in the client.

## D-003 — PostgreSQL plus Flyway as durable store
Status: **PostgreSQL history/Flyway V1 implemented and locally verified in Phase 6; owner waived import of two irrelevant MySQL records (D-027).** Jobs and typed evidence are not yet durable.
Decision: PostgreSQL owns durable history, results, and jobs; Flyway owns forward-only schema changes.
Rationale: Transactional job coordination and reproducible schemas are preferable to implicit updates.
Alternatives: Keep MySQL with ORM schema updates; store durable jobs in Valkey.
Trade-offs/consequences: Forward PostgreSQL migrations require explicit indexes and transaction design; startup must refuse unknown schema drift rather than silently mutate it. Cross-engine MySQL import is not required for this installation.
Pre-Phase 1 audit evidence: `pom.xml:52-56` included MySQL only; `EmailValidationHistory.java` and `EmailValidationHistoryRepository.java` defined the original table/repository; `application.properties:7` set `ddl-auto=update`. No Flyway migrations, PostgreSQL driver, or data inventory was present at audit time. D-025 records the current history-only migration boundary.

## D-004 — Valkey for DNS cache and rate limiting
Status: **Accepted direction; provisional TTL/failure policy** until evidence and load requirements are defined.
Decision: Valkey stores ephemeral DNS cache entries and shared rate-limit state, not authoritative jobs or results.
Rationale: Shared limits and caching across API/worker processes with a rebuildable cache.
Alternatives: In-process cache/limiter or PostgreSQL-backed limit state.
Trade-offs/consequences: Extra local service and outage behavior to define; never confuse cached lookup failures with absent MX. Rate-limit failure policy must be explicit.

## D-005 — Modular monolith with independent API and worker processes
Status: **Accepted direction; provisional module layout** until API/worker contracts are designed.
Decision: Keep one codebase and shared domain model, with separate runnable entry points and worker-only job execution.
Rationale: Operational separation of latency-sensitive HTTP and background work without distributed-service overhead.
Alternatives: One process for both roles or microservices.
Trade-offs/consequences: Shared releases and DB schema, but independent resource limits and lifecycle tests; no job processing inside arbitrary API request threads by default.
Audit evidence: Only `MailGuardApplication.java` boots the current app; `EmailValidationHistoryService.validate` performs DNS, synchronous SMTP, and persistence within a request. No separate worker exists.

## D-006 — PostgreSQL-backed durable jobs
Status: **Accepted direction; claim algorithm agreed in D-015; provisional lease/retry constants and schema** pending workload definition.
Decision: Transactionally claim PostgreSQL jobs with fenced leases; use bounded retries/backoff, reclaim expired leases, and idempotent evidence/result persistence. Assume at-least-once execution, not exactly-once side effects.
Rationale: Survive worker crashes without losing work or treating duplicate execution as a new result.
Alternatives: In-memory queue, Valkey queue, or broker.
Trade-offs/consequences: Claim/index/locking complexity and careful lease renewal; prove concurrent claims, restart recovery, and duplicate-write safety with PostgreSQL Testcontainers.

## D-007 — Bounded virtual-thread concurrency
Status: **Accepted direction; provisional limits** until measured.
Decision: Use Java virtual threads for blocking I/O only under admission limits and explicit DNS/SMTP/DB timeouts.
Rationale: Simple blocking code without permitting unlimited external or database work.
Alternatives: Unbounded virtual threads, fixed platform-thread pool, or reactive rewrite.
Trade-offs/consequences: Virtual threads reduce thread overhead, not downstream saturation; define per-stage limits, queue backpressure, and metrics before increasing throughput.

## D-008 — Evidence-based verification pipeline
Status: **Interim single-address semantics approved in D-018; internal DNS evidence implemented in D-022**. Durable evidence, historical observations, and API taxonomy remain provisional.
Decision: Record local syntax, then DNS/MX where meaningful, then authorized historical evidence as separate observations with provenance/time and explicit absent/unknown/transient states. Optional SMTP evidence requires separate policy and does not prove delivery.
Rationale: A boolean obscures missing data and network uncertainty.
Alternatives: Single valid/invalid result or SMTP as final authority.
Trade-offs/consequences: Richer API and persistence model; client must display uncertainty; existing response/history compatibility requires deliberate migration.
Audit evidence (before D-018): `EmailValidationResponse.java` exposes nullable Boolean checks plus status/message; `EmailValidationHistoryService.java:58-95` marked no MX `INVALID`, SMTP success `VALID`, SMTP failure `UNVERIFIED`, and overwrote its final message. `DnsLookupService.java` queried MX twice and collapsed transient failures. D-018 records the approved in-place safety cutover.

## D-009 — SMTP is optional, conservative, and disabled by default
Status: **Automatic SMTP path removed in D-018; future SMTP policy provisional** pending authorization and egress threat review.
Decision: No automatic sending and no unrestricted probing. SMTP verification requires explicit opt-in policy, bounded egress/concurrency, and local fake-server tests; it is not part of the baseline milestone.
Rationale: Recipient enumeration, injection, unreliable responses, and network abuse are unacceptable defaults.
Alternatives: Always probe or remove SMTP forever.
Trade-offs/consequences: Less mailbox-level evidence by default; if enabled later, document consent/authorization, timeouts, allowable targets, and unknown outcomes before deployment.
Audit evidence (before D-018): `SmtpVerificationService.java:20-101` connected on port 25 on the request path and logged full addresses; `EmailFormatValidator.java` permitted control characters that reached `RCPT TO`. No live probes were run. D-018 removed the automatic path and obsolete service.

## D-013 — Streaming per-import deduplication and row-preserving exports
Status: **Accepted flow; unimplemented**, with CSV limits, normalization, owner/access and retention policy still provisional.
Decision: Stream bounded CSV batches into durable per-import rows and retain each original ordinal. Record rejected/duplicate rows, normalize accepted addresses once, then create one job per unique normalized address within that import; a duplicate links to the first row's result. Invalid email syntax remains a verification outcome, not an invisible import rejection. Export one row per input ordinal with reason codes. Do not deduplicate contacts across owners by default.
Rationale: A 15,000-row import should not require 15,000 concurrent HTTP requests or memory proportional to the whole file, and deduplication must not silently discard user rows.
Alternatives: Load entire CSV into memory; deduplicate globally; drop duplicates or rejected rows from exports.
Trade-offs/consequences: Staging and row/result mapping use storage and require CSV size, encoding, column, formula-injection-safe export, tenant authorization and deletion rules. Test deterministic 15,000-row imports, interruption/restart and ordered exports before claiming capacity.
Audit evidence: Only `POST /api/email/validate` and `/api/email/test` exist in `EmailValidationHistoryController.java`; no import/export or tenant model exists.

## D-014 — Single-address compatibility beside asynchronous bulk jobs
Status: **Single-address cutover approved and implemented in D-018; asynchronous bulk routes still proposed and unimplemented**.
Decision: Keep the existing single-address route while adding separate asynchronous import/progress/results/export routes; do not turn `/api/email/validate` into a job-creation endpoint without versioned or approved contract migration. Remove automatic SMTP from its normal path as the accepted safety direction in D-009, and explicitly document/test the resulting response/status changes.
Rationale: Bulk requests need durable progress and retries; established single-address callers must not silently receive a job ID instead of their existing response.
Alternatives: Issue 15,000 synchronous validation requests, replace the existing route in place, or keep unsafe SMTP for wire compatibility.
Trade-offs/consequences: Two entry paths temporarily share classification rules; the safety fix changes legacy semantics. Inventory consumers before cutover and test both contracts. Do not add compatibility shims that preserve unsafe probing.
Audit evidence (before D-018): `EmailValidationHistoryService.validate` synchronously performed DNS, SMTP and persistence; `EmailValidationResponse` returned nullable booleans plus status/message. D-018 replaced probing with a passive response in place.

## D-015 — Fenced PostgreSQL leases rather than a broker
Status: **Accepted claim and completion flow; unimplemented**, with lease/backoff/failure limits provisional until tested.
Decision: Claim due/expired rows with PostgreSQL `FOR UPDATE SKIP LOCKED` in short transactions; increment a lease token on claim. Execute bounded verification work outside the claim transaction. Only the current, unexpired token may atomically write evidence, reason-coded result and terminal job state, or write a transient failure observation with its retry state. Reject stale writes; bound attempts/backoff and make duplicate result keys unique.
Rationale: At-least-once execution needs crash recovery and prevention of stale workers overwriting newer results. Valkey remains disposable.
Alternatives: Long DB transactions across DNS I/O, an in-memory/Valkey queue, or a separate broker with cross-store consistency.
Trade-offs/consequences: Polling, indexes, clock/lease policy and claim contention load PostgreSQL; a broker may be revisited after measuring queue latency and capacity. Tests must cover concurrent claims, crash/reclaim, expiry during I/O and duplicate writes with real PostgreSQL.
Audit evidence: `EmailValidationHistoryRepository` is a simple `JpaRepository` without a job entity; the source tree has no worker or migration.

## D-018 — Passive single-address API cutover
Status: **Approved in conversation; implemented and verified offline**, pending production MySQL/Docker validation.

## D-021 — Bounded email syntax and IDNA policy
Status: **Approved for Step 2; implemented and verified offline**. This is not the PostgreSQL/worker phase called Phase 2 in PLAN.md.
Decision: Support a deliberate subset of RFC 5322 local-part syntax: ASCII dot-atoms using `atext`, or a whole quoted ASCII local part with literal printable characters, spaces, and printable backslash escapes. Reject empty components, comments, folding whitespace, domain literals, obsolete forms, and non-ASCII local parts; do not claim SMTPUTF8 or complete RFC conformance. Require at least two public-hostname labels, ASCII LDH after IDNA, no empty labels or edge hyphens, and no alternate Unicode dot separators. Reject a final ASCII label consisting only of digits after IDNA; this excludes dotted IPv4 text and all-numeric terminal labels even in private DNS.
Internationalization: Normalize Unicode domain labels to NFC and encode with Java `IDN.toASCII(..., USE_STD3_ASCII_RULES)`. Compare the Unicode round-trip modulo NFC and case, and validate existing `xn--` labels; reject mappings such as `faß` to `fass`, invisible formatting characters, symbols, and malformed A-labels. Lowercase the resulting ASCII domain only; never lowercase or rewrite the local part or original address. Java IDN uses IDNA2003/Nameprep, not IDNA2008: this is not a complete IDNA2008 validity, contextual, or bidirectional-text policy. Lossless round-trip does not prove public TLD registration, mailbox reachability, or safety from cross-script homographs; those require separate policy or lookup.
Length and load: Bound raw input at 254 Java UTF-16 code units before scanning. Count the ASCII SMTP representation in octets, not Unicode input characters: local part at most 64, each A-label at most 63, dotted domain at most 253, and complete address at most 254. The existing HTTP `@Size(max=255)` still returns 400 for larger request values; a 255-character but syntactically well-formed address returns HTTP 200 with `INVALID`. Scan input without regex or network calls; reject invalid results before DNS while retaining the existing INVALID history write.
Internal result: `EmailFormatValidator.Result` carries `Reason` and normalized domain only for valid syntax. Stable codes: `VALID`, `EMPTY_ADDRESS`, `MISSING_AT`, `MULTIPLE_AT`, `EMPTY_LOCAL_PART`, `INVALID_LOCAL_PART`, `UNSUPPORTED_LOCAL_UNICODE`, `LOCAL_TOO_LONG`, `EMPTY_DOMAIN`, `INVALID_DOMAIN_LABEL`, `INVALID_IDNA`, `DOMAIN_TOO_LONG`, `ADDRESS_TOO_LONG`, `UNSUPPORTED_CHARACTER`. These reasons are internal, not new public response fields.
Trade-offs/consequences: Quoted ASCII spaces now pass; formerly accepted malformed domains, Unicode local parts, and overlong addresses now return HTTP 200/`INVALID` with an original-address history row and no DNS. Valid domains now use lowercase ASCII A-labels in DNS, response `domain`, and history `domain`. Public endpoints, response fields, and unexpected-error handling are unchanged. Full standards-aware internationalized mailboxes, storage policy, DNS/SMTP rebuild, and durable jobs remain out of scope.
Verification (2026-10-15): Focused JUnit syntax/HTTP tests cover reason codes, quoting, IDNA and byte boundaries; local synthetic bulk and HTTP smoke evidence is in PROGRESS.md. No external SMTP or DNS calls were made.

## D-022 — Bounded DNS routing evidence before durable jobs
Status: **Approved Engine 2 scope; implemented and verified offline**. This does not complete PLAN.md Phase 3 bulk intelligence.
Decision: Use the canonical lowercase ASCII domain from Engine 1; issue absolute MX queries through an injectable dnsjava resolver. Preserve MX preference order with stable equal-priority ties. Recognize only a sole priority-0 MX pointing to `.` as Null MX ([RFC 7505, §3](https://www.rfc-editor.org/rfc/rfc7505.html#section-3)); mixed or malformed MX sets are unknown. On NOERROR with no MX, check the original domain's A then AAAA for an implicit route. If MX exists, check each distinct exchanger's A/AAAA in preference order and never fall back to the original domain's addresses. Stop on the first usable target. A temporarily failed target plus a usable backup is degraded; no usable target with temporary errors is unknown/retryable. Exchanger CNAMEs are outside the address-record requirement of [RFC 5321, §5.1](https://www.rfc-editor.org/rfc/rfc5321.html#section-5.1) and stay uncertain. No SMTP/mailbox check is performed.
Conflict policy: A target A NOERROR/NODATA followed by AAAA NXDOMAIN is inconsistent and remains unknown, not negative. An earlier transient A failure followed by AAAA NXDOMAIN or an exchanger CNAME remains retryable unknown. An initial target NXDOMAIN is treated as that target being absent.
Evidence: `DnsObservation` records `MAIL_ROUTE`, `MAIL_NOT_ACCEPTED`, `NO_MAIL_ROUTE`, or `UNKNOWN`. Stable reasons include `MX_PRESENT`, `MULTIPLE_MX`, `MX_TARGET_PARTIAL`, `MX_TARGET_NO_ADDRESS`, `MX_TARGET_TEMPORARY_FAILURE`, `MX_TARGET_UNCERTAIN`, `NULL_MX`, `IMPLICIT_MX`, `DOMAIN_NOT_FOUND`, `NO_MAIL_ROUTE`, `DNS_TEMPORARY_FAILURE`, `DNS_REFUSED`, `DNS_RESOLVER_UNAVAILABLE`, `DNS_QUERY_BUDGET_EXCEEDED`, `DNS_MALFORMED_RESPONSE`, `DNS_ALIAS_LOOP`, `DNS_ALIAS_DEPTH_EXCEEDED`, and `DNS_ALIAS_FAILURE`. The model carries the canonical domain, ordered MX host/preference data, retryability, and timestamp. Initial resolver I/O, timeout, SERVFAIL, and REFUSED remain retryable unknown; no absent route is inferred from a transient failure. Typed evidence remains internal; history stores only the nullable legacy MX Boolean.
Compatibility: Keep both POST routes, response fields, 400 handling, format-invalid `INVALID`, format-valid `UNVERIFIED`, and `smtpVerified=null`. Any observed ordinary MX maps to `mxRecordFound=true` even if every exchanger lacks an address or a target lookup fails; implicit routing, Null MX, NXDOMAIN, and absent routing map to `false`; uncertain initial MX lookup maps to `null`. Target-specific messages disclose unusable, temporary, and degraded routes without claiming mailbox existence. Invalid syntax never queries DNS.
Limits/cache: Use a 2-second per-server timeout, one attempt per configured resolver, a 2-second overall retry window, at most 16 concurrent DNS observations, 24 resolver queries per observation, eight CNAME hops, 32 MX records, and 128 answer records per response. In-progress DNS I/O cannot be forcibly canceled by the overall retry window. Deduplicate identical MX targets within an observation. Exhausting the DNS query budget while MX targets remain uninspected yields retryable unknown. Do not cache in-process or via Valkey yet: positive/negative TTL caps, transient failure policy, expiry, eviction, and shared outage semantics require the future cache milestone (D-004). Every admitted attempt queries the resolver anew. No outbound HTTP lookup, SMTP, email sending, or address-level DNS logging is added.
Budget/public compatibility: `DNS_QUERY_BUDGET_EXCEEDED` distinguishes exhausted local query capacity from resolver failure. It is retryable unknown whether exhaustion occurs before an MX target or during A/AAAA resolution. If an ordinary MX was observed, its ordered hosts preserve `mxRecordFound=true` and the existing MX-target-unavailable message; without observed MX, the Boolean stays `null` and the generic DNS-unavailable message remains.
Trade-offs/consequences: Direct resolver calls avoid dnsjava `Lookup`'s hidden cache and search-suffix behavior but perform repeated DNS for repeated requests. Bounded synchronous work and a 16-slot admission gate can return retryable unknown under saturation. A usable DNS address does not prove the SMTP endpoint accepts connections or any mailbox exists. DNS evidence is not persisted as typed history, and production MySQL data, TTL behavior under a future cache, real DNS availability, and load throughput remain unverified.
Non-public address policy deferred: Only unspecified/wildcard and multicast addresses are rejected as malformed answers. Loopback, RFC 1918 private, link-local, IPv6 unique-local, documentation, and other non-public/reserved addresses currently count as DNS address evidence. Excluding them would change established route/API/history classification and existing synthetic fixtures. Do not use this evidence as a safe destination list for future SMTP; decide routability and egress filtering separately before any connection attempt.
Initial verification (2026-10-16, before MX-target checks): Offline resolver fixtures covered MX/Null MX, implicit A/AAAA fallback, NXDOMAIN, failures, CNAME, malformed replies, and concurrency. `mvn -B "-Dtest=DnsLookupServiceTest,EmailValidationApiTest" test` passed 36 tests. A JShell fixture and live Spring Boot/H2 API with a loopback-only UDP DNS server returned the expected MX, implicit, Null MX, and missing-route responses without external DNS or SMTP. The follow-up verification is recorded in PROGRESS.md.

## D-023 — Safe SMTP Verification Engine architecture and policy
Status: **Local fixture engine implemented; not deployed or integrated into the API**. Final verification is recorded in PROGRESS.md.
Decision: Keep the Engine 3 module isolated and disabled by default. The only opt-in policy, `localOnly(port)`, allows the exact numeric destinations `127.0.0.1` and `::1` on one configured port; the transport connects to that pinned `InetAddress` without DNS resolution. Hostnames, private, link-local, multicast, reserved and external destinations are unsupported. No `allowAll` path or external operator authorization exists. A production SMTP integration requires a separate approved authorization and egress design. Reuse Engine 1 syntax checks and reject any recipient that would change under ASCII transmission. Never send DATA or generate random recipient probes; catch-all status remains unknown without separately authorized evidence.
Rationale: SMTP acceptance at RCPT does not establish delivery or mailbox existence. Unrestricted probing, DNS rebinding, enumeration and network pivots are unsafe defaults; local socket fixtures exercise the protocol without exposing external destinations.
Trade-offs/consequences: A bounded conversation permits up to four concurrent local sessions by default, with per-stage and total timeouts, bounded replies and automatic socket cleanup. EHLO falls back to HELO once only for unsupported commands. Bare 550, policy refusals, 552 and temporary errors do not claim a nonexistent mailbox. There is no boolean mailbox-success adapter: the typed observation only reports recipient-stage evidence. Interrupted blocking reads can take up to the configured read timeout to stop. The production API remains passive and `smtpVerified` stays null. Finalized Engine 2 routing and API changes are present in this checkout through `origin/main` at `aa1c865`; the SMTP engine remains isolated and disabled.

## D-024 — Conservative internal evidence classification
Status: **Implemented and verified offline on the PR #5 feature branch; not deployed or persisted**. This is not PLAN.md Phase 5 local product.
Decision: `classification` contains immutable syntax/DNS/optional SMTP evidence, source and stage timestamps, stable category/reason codes, retryability, a computation timestamp, and fixed human-readable diagnostics. SMTP snapshots retain outcome, reason, numeric reply, sanitized enhanced code and observation time, but never host, raw diagnostic, transcript, or full recipient address. DNS evidence retains the canonical domain and ordered MX hosts. No TTL or expiry exists yet, so freshness is unknown rather than guessed.
Policy: Invalid syntax dominates. DNS NXDOMAIN means `DOMAIN_NOT_FOUND`; sole Null MX means `MAIL_NOT_ACCEPTED`; a usable MX or implicit A/AAAA route means `ROUTE_AVAILABLE` without a mailbox claim. No usable route, absent DNS, and transient or ambiguous outcomes mean `ROUTE_UNCERTAIN`. Only RCPT 250/251 with matching acceptance reason means `RECIPIENT_ACCEPTED_UNCONFIRMED`. Only RCPT 550 with enhanced `5.1.1` and `RECIPIENT_NOT_FOUND` means `RECIPIENT_REJECTED`. Contradictory definitive DNS and SMTP evidence means `ROUTE_UNCERTAIN`, irrespective of observation order. A route classification is not a deliverability or mailbox guarantee.
Compatibility: The classifier is callable by future workers, but it does not connect to SMTP, change the D-018/D-022 passive API response or MySQL history schema, or activate persistence. PLAN.md Phase 5 still refers to UI/Compose/CI/operations; classification alone does not complete it.
Trade-offs/consequences: Typed evidence is in memory only; historic observations have no validity window, so conflicting evidence cannot be reconciled by age. Production authorization, PII retention/access, durable storage and new API taxonomy need separate approval.
Verification (2026-10-16): Focused JUnit classifier tests passed 8/8; after the `MULTIPLE_MX` matrix addition, `mvn -B test` and `mvn -B package` each passed 185/185 tests, including passive API and local SMTP fixture tests. Compiled JShell smokes classified synthetic implicit routing as `ROUTE_AVAILABLE`, contextual SMTP rejection as `RECIPIENT_REJECTED`, and contradictory Null MX plus SMTP rejection as `ROUTE_UNCERTAIN`. No external DNS/SMTP hosts were contacted.

## D-025 — Phase 6 history-only PostgreSQL cutover
Status: **Merged in PR #6 and verified locally**; owner waived MySQL import in D-027. Production permissions and recovery remain unverified.
Decision: Replace the MySQL runtime driver with PostgreSQL 17 and Flyway V1 for a **fresh, empty** database. Flyway alone creates `email_validation_history`; Hibernate validates but never creates or updates production tables. Keep the established synchronous POST routes, response/status/error behavior, nullable legacy booleans, and full-address history row. Store `created_at` as `TIMESTAMPTZ` mapped to Java `Instant`, with a database default and a `(created_at DESC, id DESC)` index. Read recent history with a pageable `Slice` ordered by timestamp and id; require a page-size limit before exposing it through an authorized endpoint. Keep DNS outside the repository `save` transaction and close the persistence context before rendering the HTTP response. Cap the Hikari pool with environment-controlled settings; the default PostgreSQL isolation is `READ COMMITTED`, not MySQL InnoDB's usual `REPEATABLE READ`.
Migration boundary: Flyway V1 contains no MySQL data import, baseline, data deletion, table drop or repair. D-027 makes migration of the owner's two legacy MySQL records intentionally out of scope. An existing populated PostgreSQL schema without Flyway history fails startup instead of being adopted; an already migrated, compatible database must retain its rows on restart. Do not modify an applied V1, reset a populated PostgreSQL database or treat the unused MySQL database as recovery for new writes.
Evidence boundary: Do **not** persist `ClassificationResult` or SMTP/DNS evidence in V1. The classifier is internal and unused by the production API; no consent, access, retention or freshness/TTL policy exists for address-linked observations. A future approved additive migration should reference a history/job id, use typed stage/outcome/reason/source, retryability, observation and classification times plus a classifier version, and keep conflicting observations as separate records with a conflict result. Absence means no observation row, never fabricated `UNKNOWN`; unknown remains a typed outcome when actually observed. Keep raw addresses, MX hosts, SMTP hosts, transcripts and reply text out of evidence rows; store only sanitized numeric/enhanced SMTP codes if needed to replay a classification. No historic V1 evidence backfill, inferred TTL, or automatic SMTP activation. Privacy controls and idempotent job ownership must be defined before any such migration.
Trade-offs/consequences: The owner's two old MySQL rows remain outside the new PostgreSQL installation; the old database remains untouched. Full email addresses still reside in history without an approved retention/access policy; this branch must not expose a history API. `READ COMMITTED` readers can observe committed changes between statements; transactions cover only individual saves and pageable reads, not DNS. This is the history portion of durable core, **not** PLAN.md Phase 2 job/worker completion or Phase 5 local product.
Verification (2026-10-16): `mvn -B clean test`, `mvn -B clean verify`, and `mvn -B package` each passed 191 tests, including six PostgreSQL 17 Testcontainers cases for fresh/repeated migrations, refusal of an untracked nonempty schema, Hibernate validation, nullable values, ordering, constraints and rollback. No external DNS, SMTP, personal address or production MySQL was used.
